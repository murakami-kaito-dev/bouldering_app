# 07 検索とフィルタリング

## 本体での対応箇所

- `lib/presentation/providers/gym_name_search_provider.dart` — ジム名/住所の部分一致検索＋関連度ソート
- `lib/presentation/providers/gym_search_filter_provider.dart` — 都道府県×種別の複合フィルタ＋件数のリアルタイム表示
- `lib/presentation/pages/gym_selection_page.dart` — インクリメンタル検索UI
- `lib/presentation/pages/gym_search_page.dart` — 条件検索UI（※このページには build 内副作用による無限リビルドのバグ候補があった。`refactor-candidates.md` B-10）

## 学べるポイント

1. **デバウンス**: 1文字ごとに検索を走らせず、入力が300ms止まってから実行。`Timer` をキャンセルして張り直すのが定石。画面の「検索実行回数」で効果が見える。
   - 類似概念のスロットル（一定間隔で必ず実行）との違いも説明できるように。
2. **関連度ソート**: 前方一致 > 部分一致 > 名前順。本体も同じ発想でジム名検索を並べている。
3. **検索ロジックの純粋関数化**: `searchGyms(全件, 条件) → 結果` に切り出すと、ウィジェット無しでユニットテストできる。UIに検索ロジックを書き込まない。
4. **派生Provider**: 条件Providerを watch する結果Providerを作ると、「条件が変われば結果が自動で再計算される」宣言的な構造になる。

## クライアント検索 vs サーバ検索（面接での比較ポイント）

| | クライアント側（本体・このデモ） | サーバ側 |
|---|---|---|
| 前提 | 全件を最初に取得できる規模（本体はジム全件を起動時ロード） | データが大きい/更新頻度が高い |
| 応答速度 | 即時（通信なし） | 通信往復が必要（デバウンス必須） |
| 実装 | contains/startsWith | SQL LIKE, 全文検索, Elasticsearch |

本体はジム数が数百件規模なのでクライアント側で完結させている。データが増えたらサーバ検索に移す判断になる。
