# 09 テキストモデレーション（NGワードフィルタ）

## 本体での対応箇所

- `lib/infrastructure/services/local_text_moderation_service.dart` — 端末内判定の実装
- `lib/infrastructure/data/ng_words_data.dart` — NGワード辞書（アプリ同梱）
- `lib/domain/usecases/validate_post_content_usecase.dart` — 投稿前バリデーション
- `lib/shared/utils/ng_word_validator.dart` — プロフィール編集用の別経路（※UseCase経由と2経路あるのは本体のリファクタ候補）
- 適用箇所: 投稿本文・ユーザー名・自己紹介・好きなジム

## なぜこの機能があるか

**App Store Guideline 1.2**: UGC（ユーザー生成コンテンツ）を扱うアプリは、不適切コンテンツのフィルタ・通報・ブロックの仕組みが審査必須。本体の開発履歴（PR #2〜#8、2025年10月）はまさにこの審査対応の集中実装だった。

## 学べるポイント

1. **正規化してから比較**: 入力を `toLowerCase()` してから小文字辞書と比較する。本体は両辺を正規化しているため、辞書に大文字バリアント（'FUCK', 'Fuck'）を重複登録しているのは無意味（本体のリファクタ候補として記録済み）。全角半角・カタカナひらがなの正規化まで踏み込むとより堅い。
2. **検出結果の返し方**: bool だけでなく「どの語が引っかかったか」を返すと、ユーザーに修正箇所を示せる。
3. **端末内 vs サーバ判定**:
   - 端末内（本体方式）: 通信不要で即時。辞書更新にアプリ更新が必要。改造クライアントには無力
   - サーバ: 辞書を即時更新できる最終防衛線。遅延あり
   - 本格運用は両方併用（端末=UX、サーバ=防衛線）
4. **単純contains の限界**: 誤検知（Scunthorpe problem: 無害な語の内部にNG語が含まれる）と回避（l33t表記、記号挟み）。面接ではこの限界と、機械学習ベースのモデレーションAPI（Perspective API等）への発展を語れると良い。
