## 楽観的更新とは

APIの成功を**待たずに**先にUIを書き換え、失敗したら巻き戻す方式。
「いいね」「お気に入り」「フォロー」のような高頻度・低リスク・冪等な操作の定石。

対義語は悲観的更新（APIの成功を待ってからUIを変える）。決済のような取り消せない操作はこちら。

## 学べるポイント

1. **基本形**: 先にUI更新 → API → 失敗なら巻き戻し+エラー通知。
2. **連打対策（inFlight管理）**: 通信中の項目への追加操作は無視する。無視しないと「ON→OFF→ON」のリクエストが順不同で着弾してサーバとUIがズレる。
3. **巻き戻しは反転で**: 「操作前の値を保存して復元」より「反転」の方が、別項目の連続操作と競合しにくい。
4. **状態の置き場所**: この操作の状態は複数画面（一覧・詳細・お気に入りページ）で共有されるので、画面ローカル（setState）ではなくProviderに置くべき。本体の `gym_detail_page` はここが自前管理になっていて改善候補。

## 面接での定番質問

- 「いいねの即時反映はどう実装しますか？」→ 楽観的更新＋失敗時ロールバック＋inFlightガード、の3点セットで答える。
- 「サーバとの整合性はどう担保しますか？」→ 操作を冪等にする（POST/DELETEを「〜という状態にする」設計にする）。本体のバックエンドもお気に入り解除を冪等（既に削除済みでも成功扱い）にしている。
- 「オフラインだったら？」→ 失敗扱いで巻き戻すのが最小実装。進んだ設計はローカルキューに積んで再送（このアプリではやっていない）。
