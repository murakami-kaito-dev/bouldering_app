cf. マシン構成について

- 数分のダウンタイム: 変更中はDBアクセス不可
- メンテナンス窓口: 深夜など利用者の少ない時間帯推奨

∴ 結論: 2vCPU, 8GBで開始して、監視しながら必要に応じてスケールアップが最適

<開発版>無効
 → 開発中，同じタグで頻繁に更新するため
<本番版>有効
 → 本番では一度デプロイしたイメージの変更を防ぐため
 → デプロイ済みイメージの改ざん防止

cf. 📦Artifact Registry設定の詳細説明：不変のイメージタグ
意味: 一度プッシュしたタグ（例:  v1.0.0）を上書きできなくする機能
- 有効時: 同じタグで再プッシュ不可（エラーになる）
- 無効時: 同じタグで何度でも上書き可能


- クリーンアップポリシー：
<開発版>テストを実行
 →まず削除対象を確認してから本番適用
<本番版>アーティファクトを削除
 → 古いイメージを自動削除してコスト削減（ただし、保持期間は30日以上推奨）
 → クリーンアップポリシーの設定例
本番環境の推奨設定:
  ・ポリシー1：古いイメージを削除
    - 名前：production-cleanup-delete
    - ポリシータイプ：条件付き削除
    - タグの状態：タグなし
    - バージョン接頭辞：(空欄)
    - パッケージ接頭辞：(空欄)
    - アップロード後の期間(最小)：30d
    - アップロード後の期間(最大)：(空欄)
    ∴ タグ無しで30日以上経過したイメージを削除

  ・ポリシー2：最新版を保持
    - 名前：production-keep-latest
    - ポリシータイプ：最新バージョンを保持
    - 保持数：10
    - バージョン接頭辞：(空欄)
    ∴ 最新10個のイメージは常に保持

  cf. ⚠️ 重要な補足
  本番タグの保護について：
  - prod-やrelease-タグの保護は、タグを付けること自体が保護になります
  - 「条件付き削除」で「タグなし」を選択しているため、タグ付きイメージは削除されません

  cf. 🎯 設定手順
  1. 1つ目のポリシー作成
  - 「ポリシーを追加」→「条件付き削除」を選択
  - 上記の設定値を入力
  2. 2つ目のポリシー作成
  - 再度「ポリシーを追加」→「最新バージョンを保持」を選択
  - 保持数: 10 を設定

  cf. 💡 この組み合わせの効果
  - ✅ タグ付きイメージ → 永久保持
  - ✅ 最新10個 → 保持
  - ❌ タグなし + 30日経過 + 最新10個以外 → 削除

cf. 📦Artifact Registry設定の詳細説明：クリーンアップポリシー
意味: 古い・未使用のイメージを自動削除してストレージコストを削減
- テストを実行:  削除対象を表示するだけ（実際には削除しない）
- アーティファクトを削除: 実際に削除を実行


- Artifact Analysis：
<開発版>有効
→ 脆弱性スキャンの前提として必須
<本番版>有効
→ 脆弱性スキャンの前提として必須

cf. なぜ開発版では INSTANCE_CONNECTION_NAME が不要だったか
・A. コードの条件分岐が原因
- environment.ts（44–58行目）で、本番だけ必須チェックに含めています。
export function validateEnvironment(): void {
  const required = ['FIREBASE_PROJECT_ID'];

  if (config.server.isProduction) {  // ← ここがポイント
    required.push('DB_PASSWORD', 'INSTANCE_CONNECTION_NAME');
  }

  const missing = required.filter(key => !process.env[key]);

  if (missing.length > 0) {
    throw new Error(`Missing required environment variables: ${missing.join(', ')}`);
  }
}

- 環境別の必須チェック
環境	NODE_ENV	必須チェック
開発	development	FIREBASE_PROJECT_ID のみ
本番	production	FIREBASE_PROJECT_ID, DB_PASSWORD, INSTANCE_CONNECTION_NAME

∴ 開発版では NODE_ENV=development のため、INSTANCE_CONNECTION_NAME のチェックがスキップされていた

・FLAVOR
- 手動で設定した値
- --dart-define=FLAVOR=prod としてエイリアスで明示的に設定した値
- 値：prod(本番版) / dev(開発版)
- 用途：Dartコード内で環境を識別するために利用できる

・FLUTTER_APP_FLAVOR
- Flutter自動生成： --flavor "Runner Prod"からFlutterが自動的に生成する
- 値："Runner Prod"(本番版) / "Runner Dev"(開発版)
- 用途：iOS/AndroidのネイティブFlavorシステムとDartの橋渡し

・(結果)コード内で出力される値：
- FLAVOR = "prod" （手動設定）
- FLUTTER_APP_FLAVOR = "Runner Prod" （Flutter自動生成）

∴ FLAVOR：自分で意図的に設定した値
∴ FLUTTER_APP_FLAVOR： --flavorオプションの値をFlutterが自動的にDart環境変数として提供

■ Cloud SQL 削除手順
・Cloud SQL(開発版)は高額のため，削除/停止する
→ 使わないときは基本的に「停止」する．
→ (「削除」するときは)次回本番版デプロイ前のテスト実行の時に，
  再度開発版Cloud SQLを運用稼働して，テストする．
  それまではインスタンスを削除して，料金発生を抑える．
※ Cloud SQLには，真の意味で100%「中断・停止する」という選択肢がない
  （理由：常に稼働させて監視する必要があるため）

・削除/停止 前に，本番版デプロイ最新版のCloud SQLのテーブル構造，データをエクスポートしておき，
「Cloud Storage(リモート)」「ローカルPC環境」の２つに保存しておく．
→ 保管方法は任意だが，わかるようにしておくこと．
→ 既存のフォルダ・ファイル名がすでに作成してあるので(2025.09.19)，踏襲して保存・補完する．

  - 開発用(削除したい)Cloud SQLインスタンスをクリック

cf. ✅ Cloud SQL の課金内訳（ざっくり）
・CPU / メモリ（マシン稼働代）
  → インスタンスが動いている限り課金される。
  → 停止するとゼロになる。
・ストレージ代（ディスク容量）
  → インスタンスが停止中でも必ずかかる。
  → 100GB SSD ならおおよそ 月数百円〜千円。
・バックアップ代
  → バックアップ保持日数 × ストレージに依存。
  → 数十円〜数百円/月程度。

cf. ✅ 停止 vs 削除 の削減率イメージ
・現在 (2vCPU / 8GB RAM / 100GB SSD)
  → 毎月の料金の 大半（70〜90%）が CPU/RAM の利用料。
  → 残りの 10〜30%がストレージ代・バックアップ代。
・停止した場合
  → CPU/RAM 代がゼロになるので 全体の70〜90% 削減できる。
  → ただしストレージ代は残るので 10〜30% は課金が続く。
・削除した場合
  → 100% 削減。
