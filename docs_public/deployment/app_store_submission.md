- [ ] このTeam IDは後でXcodeで使用します

**Step 3: Bundle ID (App ID) を登録**
- [ ] 左メニューから「Certificates, Identifiers & Profiles」をクリック
- [ ] 「Identifiers」をクリック
- [ ] 「+」ボタンをクリックして新規作成
- [ ] 「App IDs」を選択して「Continue」

- [ ] 以下を入力:

  - Bundle ID: 「Explicit」を選択（下記補足参照）
  - Bundle ID: `com.yourcompany.yourapp` を入力
- [ ] Capabilities/App Services: 基本的な機能のみ使用するため、特に追加選択は不要（下記補足参照）
- [ ] 「Continue」→「Register」をクリック

> **🛠️ 補足: Explicit vs Wildcard Bundle ID**
> <small>
>
> **Explicit Bundle ID（明示的）**
> - 特定の1つのアプリ用のID（例: `com.yourcompany.yourapp`）
> - App Storeに提出する場合は**必ずExplicitを選択**
> - プッシュ通知などの機能が使用可能
>
> **Wildcard Bundle ID（ワイルドカード）**
> - 複数のアプリで共有できるID（例: `com.km.*`）
> - 開発・テスト用途向け
> - App Store提出には使用不可
> - 一部の機能（プッシュ通知等）が使用不可
> </small>

> **🛠️ 補足: Capabilities（機能）について**
> <small>
>
> **Capabilities/App Services/Capability Requestsとは**
> アプリが使用する特殊な機能を事前に宣言する設定です。
>
> **よく使われる機能例**:
> - **Push Notifications**: プッシュ通知
> - **Sign in with Apple**: Appleでサインイン
> - **In-App Purchase**: アプリ内課金
> - **iCloud**: クラウドストレージ
> - **HealthKit**: ヘルスケアデータ連携
> - **Game Center**: ゲーム機能
>
> **現在のアプリ（Bouldering App）の場合**:
> - Firebase認証を使用 → Sign in with Appleは不要
> - 課金機能なし → In-App Purchase不要
> - 基本的な機能のみ → **特に追加選択は必要ありません**
>
> ※後から必要になった場合はいつでも追加可能です
> </small>

#### 証明書作成

**Step 4: iOS Distribution Certificate を作成**
- [ ] 「Certificates」をクリック
- [ ] 「+」ボタンをクリック
- [ ] 「Apple Distribution」を選択して「Continue」
- [ ] CSR（証明書署名要求）ファイルの作成とアップロード:

  > **🛠️ 補足: CSR（Certificate Signing Request）とは**
  > <small>
  >
  > **CSRは証明書を作るための「申請書」**のようなものです。
  >
  > **なぜ必要？**
  > - Appleがあなたを「正規の開発者」として認証するため
  > - アプリが本当にあなたが作ったものだと証明するため
  > - App Storeで配布する権限を得るため
  >
  > **仕組みの簡単な説明**:
  > 1. **CSR作成時**: あなたのMacで「秘密鍵」と「公開鍵」のペアが作られる
  > 2. **CSRファイル**: 公開鍵とあなたの情報が含まれる申請書
  > 3. **Appleに送信**: AppleがCSRを確認して証明書を発行
  > 4. **証明書受け取り**: Appleが「この開発者は信頼できる」と認めた証明
  >
  > **例え話**:
  > - CSR = パスポート申請書
  > - 証明書 = 発行されたパスポート
  > - これによりApp Storeという「国」に入国（アプリ配布）できる
  >
  > ⚠️ **重要**: CSRは1回作れば、複数の証明書作成に再利用可能
  > </small>

  **CSRファイルの作成手順**:
  1. **キーチェーンアクセスを開く**:
     - Spotlight検索（⌘ + スペース）で「キーチェーンアクセス」と入力
     - または、アプリケーション → ユーティリティ → キーチェーンアクセス

  2. **証明書要求画面を開く**:
     - 上部メニューバーから「キーチェーンアクセス」をクリック
     - 「証明書アシスタント」→「認証局に証明書を要求...」を選択

  3. **証明書情報を入力**:
     - **ユーザのメールアドレス**: Apple IDのメールアドレスを入力
     - **通称**: あなたの名前（例: [YOUR_FULL_NAME]）
     - **CAのメールアドレス**: 空欄のままでOK
     - **要求の処理**: 「ディスクに保存」を選択
     - 「鍵ペア情報を指定」にチェック

  4. **保存**:
     - 「続ける」をクリック
     - ファイル名: `CertificateSigningRequest.certSigningRequest`（デフォルトのまま）
     - 保存場所: デスクトップ（後で見つけやすい場所）

  5. **鍵ペア情報**（表示された場合）:
     - 鍵のサイズ: 2048ビット
     - アルゴリズム: RSA
     - 「続ける」→「完了」
- [ ] 保存したCSRファイルをアップロード
- [ ] 「Continue」→証明書をダウンロード
- [ ] ダウンロードした証明書（.cer）をダブルクリックしてキーチェーンに追加

**Step 5: App Store Distribution Provisioning Profile を作成**
- [ ] 「Profiles」をクリック
- [ ] 「+」ボタンをクリック
- [ ] 「Distribution」セクションの「App Store Connect」を選択して「Continue」
  - 注意: 「Development」ではなく「Distribution」セクションから選択
- [ ] App ID: `com.yourcompany.yourapp` を選択
- [ ] 先ほど作成した Distribution Certificate を選択
- [ ] Provisioning Profile Name: `Bouldering App Distribution` と入力
- [ ] 「Generate」をクリック
- [ ] プロファイルをダウンロード
- [ ] ダウンロードした.mobileprovisionファイルをダブルクリックしてXcodeにインストール

> **📝 補足: バンドルIDとは**
> <small>
> バンドルID（Bundle Identifier）は、アプリの一意な識別子のこと。形式は企業のドメイン名を逆にした形（例: com.yourcompany.yourapp）で、以下の特徴がある：
> - **ユーザーには基本的に見えない**（アプリ名と開発者名のみ表示）
> - **App Storeでアプリを一意に識別**するために使用
> - **一度公開すると変更不可**（変更する場合は新しいアプリ扱い）
> - Firebase、Push通知などの外部サービス連携で必要
> </small>

> **📝 補足: 開発者名について**
> <small>
> 開発者名は、Apple Developer Programに登録した際の名前を指す：
> - **個人開発者の場合**: 登録時の氏名
> - **法人の場合**: 会社名
> - **確認方法**: [developer.apple.com](https://developer.apple.com) → Account → Membership
> - **App Storeでの表示**: アプリ名の下に「[開発者名]」として表示
> - 基本的に変更不可（法人の場合は会社名変更時のみ可能）
> </small>

> **📝 補足: バージョン番号とビルド番号の違い**
> <small>
> **バージョン番号（1.0.0）**: ユーザー向けの番号。App Storeで表示される
> - メジャー.マイナー.パッチ形式（例: 1.0.0 → 1.0.1 → 1.1.0）
> - 機能追加、バグ修正、UI改善など**ユーザーに見える変化**があるときに変更
>
> **ビルド番号（+1）**: 開発者向けの管理番号。App Storeには表示されない
> - 必ず前回より大きい数字にする（減らせない）
> - 審査リジェクト、スクショ差し替え、説明文修正など**中身は同じだが再提出**するときに増やす
>
> **例**:
> - `1.0.0+1` → 初回提出
> - `1.0.0+2` → リジェクトされて修正後の再提出（アプリの中身は同じ）
> - `1.0.1+3` → バグ修正版（ユーザーに見える変更あり）
> - `1.1.0+4` → 新機能追加
> </small>

## ⚠️ 重要: Code Signing Identityの確認と修正

### 必須確認事項（Archive作成前）

**Build Settingsで証明書設定を確認**:

1. **確認手順**:
   - Xcodeでプロジェクトを開く
   - 左サイドバーで「Runner」プロジェクトを選択
   - 中央エリアで「Runner」ターゲットを選択
   - 上部タブで「Build Settings」をクリック
   - 検索窓に「Code Signing Identity」と入力

2. **正しい設定値**:

| Configuration | 必須の証明書 | 用途 |
|---|---|---|
| Debug-Runner Dev | Apple Development | `fdev`実行時の開発テスト |
| Debug-Runner Prod | Apple Development | `fprod`実行時のデバッグ |
| Release-Runner Dev | Apple Development | 開発版の最適化ビルド |
| **Release-Runner Prod** | **Apple Distribution（必須）** | **App Store提出用Archive** |
| Profile-Runner Dev | Apple Development | パフォーマンス測定 |
| Profile-Runner Prod | Apple Development | パフォーマンス測定 |

3. **修正が必要な場合**:
   - **Release-Runner Prod**が**Apple Development**になっている場合は修正必須
   - 該当行をクリック → **Apple Distribution**または**iOS Distribution**を選択
   - 選択肢にない場合は、Distribution証明書の作成が必要（Phase 1.2参照）

### なぜ設定が変わることがあるか

- **Automatically manage signing**を有効にすると、すべてDevelopmentに変更される場合がある
- 実機テスト設定時に誤って変更される可能性
- Xcodeアップデート時にリセットされることがある
- 新規プロジェクトのデフォルトはすべてDevelopment

> **⚠️ Archive作成前に必ずRelease-Runner ProdがApple Distributionになっていることを確認してください。これが間違っていると、App Storeに提出できません。**

## Phase 4: Xcode Archive作成

> **🚨 重要：バックエンド同期デプロイ**
> 
> **App Store Connect申請時の必須事項**：
> - フロントエンド（iOS）とバックエンド（Cloud Run）の変更は**同じタイミング**でデプロイすること

**Appleの「トラッキング」定義**:

- ❌ 広告配信・ユーザー行動分析は一切実施しない

# 🚨 よくある問題と対処法

## Archive失敗
- **原因**: 証明書・プロビジョニングプロファイルの問題
- **対処**: Apple Developer Portalで証明書を再確認、Xcodeで更新

## アップロードエラー
- **原因**: Bundle IDの不一致、バージョン重複
- **対処**: Info.plistとApp Store Connectの設定を再確認

## 審査リジェクト
- **原因**: ガイドライン違反、機能不具合、メタデータ問題
- **対処**: リジェクト理由を確認し、該当箇所を修正して再提出

## 位置情報権限エラー
- **原因**: Info.plistの説明文不備
- **対処**: NSLocationWhenInUseUsageDescriptionを適切に設定

# 📱 アプリアップデート時の手順

## 機能追加・バグ修正後のリリース手順

### 1. バージョン番号の更新（必須）
```yaml
# pubspec.yaml
version: 1.0.1+2  # バージョンとビルド番号を更新
# 例: 1.0.0+1 → 1.0.1+2（バグ修正）
#     1.0.0+1 → 1.1.0+2（新機能追加）
#     1.0.0+1 → 2.0.0+2（メジャーアップデート）
```

### 2. 確認が必要な項目

**毎回確認**：
- [ ] pubspec.yamlのバージョン番号を更新
- [ ] 新機能の動作テスト（シミュレータ・実機）
- [ ] 既存機能への影響確認

**必要に応じて確認**：
- [ ] 新しいCapabilityを使用する場合 → App IDを更新して、Provisioning Profile再生成
- [ ] 新しい権限が必要な場合 → Info.plistに説明文追加
- [ ] 新しいAPIキーやサービス追加 → 環境変数の更新

### 3. 証明書関連で再作成が必要なケース

**証明書の再作成は不要**（1年間有効）：
- 通常のバグ修正
- 機能追加
- UI変更

**Provisioning Profileの再作成が必要**：
- 新しいCapability追加時（Push通知、HealthKit等）
- Bundle ID変更時
- 証明書の期限切れ時（1年後）

### 4. Archive作成とアップロード

```bash
# 1. クリーンビルド
flutter clean
flutter pub get
cd ios && pod install && cd ..

# 2. 本番ビルド
fbprod

# 3. Xcodeでアーカイブ作成
open ios/Runner.xcworkspace
# Product → Archive

# 4. App Store Connectにアップロード
```

### 5. App Store Connect更新

**必須項目**：
- [ ] 新しいビルドを選択
- [ ] 「このバージョンの新機能」を記載

**任意項目**：
- [ ] スクリーンショットの更新（UIが大きく変わった場合）
- [ ] アプリ説明文の更新（新機能追加時）
- [ ] キーワードの最適化

### 6. 審査提出
- [ ] 審査提出前の最終動作確認
- [ ] 審査提出（通常1-3日で結果）

## ⚠️ よくある注意点

1. **バージョン番号を忘れずに更新**
   - 同じバージョン番号では提出できません

2. **証明書の期限確認**
   - Apple Developer Portal → Certificates で期限を確認
   - 期限切れ前に更新推奨

3. **Capability追加時は要注意**
   - Provisioning Profileの再生成を忘れずに

4. **審査リジェクト対応**
   - リジェクト理由を修正
   - ビルド番号のみ更新（例: 1.0.0+1 → 1.0.0+2）
   - 再提出
